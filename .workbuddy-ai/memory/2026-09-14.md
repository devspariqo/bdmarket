### Gotchas reinforced this session
- The `agent-browser` daemon dies after the *first* `eval` on heavy pages, so a click and its
  verification must be a single `eval` or two evals inside one Bash call with `sleep` between.

- `await` inside a chained `agent-browser eval` returning a Promise → SIGTERM.

  Workaround: `curl` the login API, grab `bdm_session` from `set-cookie`, then set it in the
  browser with `document.cookie='...; path=/'` and re-open the page.

### 20. `<meta name="theme-color">` was duplicated and the hardcoded one won
**This is the subtle one.** `app/layout.tsx` had `themeColor: '#006a4e'` in the static

`theme-color` in the document — so the admin's saved colour was silently overridden on every
page load. Same class of bug as #19: a hardcoded value shadowing the merchant's setting.

Fix: dropped `themeColor` from the `viewport` export entirely (with a comment explaining why)
so `RootLayout` is the single source. Verified the served HTML now has exactly **one**
`theme-color` tag carrying the live `#ff6600`.

**Rule for this project:** any Next `viewport`/`metadata` static export that would duplicate a
dynamic `<meta>` in `RootLayout` must be left unset — Next emits it first and wins.

## Session 4 — footer payment grid, payment logo uploads, favicon, product images, product page

### 21. Favicon did not update when the admin uploaded one — TWO causes
This had two independent faults, either of which alone would break it:

**(a) Next's file-based metadata overrode the setting.** `app/icon.svg` existed, which is Next's
convention for auto-generating `<link rel="icon">`. Next emitted that tag **last** and with a
content hash (`/icon.svg?cb61bfe9e28b99db`), and browsers take the last icon — so it beat the
tag generated from `site_favicon`. **Fix:** moved the artwork to `public/icon.svg` so it is no
longer a metadata-convention file. `app/` must contain no `icon.*` / `apple-icon.*` if the
favicon is to be admin-controlled.

**(b) The MIME type was hardcoded.** `<link rel="icon" href={favicon} type="image/svg+xml">` —
so an uploaded PNG was announced as SVG and browsers rejected it. **Fix:** new `lib/icons.ts`
with `mimeForIcon()` deriving the type from the extension.

Also fixed: `apple-touch-icon` was hardcoded to `/icon.svg`, and `app/manifest.ts` hardcoded
`/icon.svg` + `/favicon.svg` for the installed-app icons. Both now read `site_favicon`.

Before: 3 icon tags (PNG-as-SVG, hardcoded apple-touch, Next's `app/icon.svg`).
After: 2 tags, both pointing at the uploaded PNG with `type="image/png"`.

  the defaults when nothing is saved), `blankPaymentLogo()`.
- **`components/PaymentMark.tsx`** — `PaymentMark` (typographic badge in the brand colour) and
  `PaymentBadge` (uploaded `<img>` or the mark). No `'use client'` **on purpose**: the footer is
  a server component and the admin manager is a client component, and both import this file.
- **`components/admin/PaymentLogoManager.tsx`** — repeater: upload/replace/remove logo, brand
  name, short mark, colour, caption, reorder up/down, delete, reset to defaults, and a live
  dark-background 3×3 preview. Save reuses `PATCH /api/admin/settings`.
- **`app/admin/settings/payment-logos/page.tsx`** + nav entry under Settings.

**Storage decision:** one JSON setting (`payment_logos`, group `payment_logos`) rather than a row
per brand, so the merchant can add/remove/reorder without a schema change. The existing settings
API already `JSON.stringify`s object values, so **no new API route was needed** — and we inherit
cache invalidation and the audit log for free.

**Deliberate choice:** the fallback marks are typographic badges, **not** reproductions of the
official logos. These are trademarks; a hand-drawn approximation would look wrong and misrepresent
the brand. The merchant uploads real artwork when they have it.

### 23. Product image upload system (new feature)
`components/admin/ProductEditor.tsx` only accepted pasted URLs. Added

### 24. Product page: description / specifications / reviews
The old page was three stacked sections with a comment claiming they were tabs.

- **`components/store/ProductTabs.tsx`** — real tabs (Description | Specifications | Reviews N).
  **All three panels are always rendered and toggled with the `hidden` attribute**, not unmounted.
  That is deliberate: it keeps specs and reviews in the initial HTML for crawlers, and makes tab
  switching a class toggle rather than a re-render. Panes are passed in as pre-rendered nodes, so
  parsing/grouping runs on the server and only tab state ships to the client.
- **`components/store/ProductDescription.tsx`** — was `text.split('\n\n')` into `<p>`. Now parses
  the small Markdown subset people actually type: `##`/`###` headings, `-`/`*`/`•` bullets,
  `1.` numbered lists, `>` quotes, `**bold**`, blank line = new block. Plus an "At a glance"
  summary card. Not a full Markdown parser — no dependency, no raw-HTML XSS surface.
- **`components/store/ProductSpecs.tsx`** — groups into Product Information / Specifications /
  Material & Care / Shipping & Origin, drops empty rows *and* empty groups, adds barcode, weight,
  dimensions and a colour-coded Availability dot. Verified: a fitness band correctly omits
  Barcode/Weight/Dimensions and keeps Country of origin.
- **`components/store/ProductReviews.tsx`** — clickable rating-distribution bars that filter,
  4-way sort (recent / helpful / high / low), "N% recommend", verified badge, relative dates,
  "Helpful" votes, and progressive "show more" paging. All client-side over already-fetched
  reviews, so filtering costs no request.
- Product page sidebar is now `lg:sticky` and its "Payment Options" uses the **same**
  `getPaymentLogos()` source as the footer, so the two can never disagree.

**`highlights`** for the "At a glance" card are *derived* from fields the merchant already filled
in (fabric, fit, occasion, attributes, care, origin, low stock, COD, returns) rather than asking
them to write a summary — so it works on every existing product with no data migration.
